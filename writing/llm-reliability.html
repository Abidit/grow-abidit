How We Kept an LLM Feature Reliable at 1.5M-Learner Scale

Five things that broke, and what fixed them

For a little over four years I owned the frontend and eventually the AI features for Programiz's B2B Pro Teams platform, used by 1.5M+ learners across 40+ institutions.

One of those features was SensAI, a GPT-4o-powered hint system that read a learner's current code state and returned either a short code snippet (one to a few lines) or a plain-language nudge toward thinking through edge cases, without handing over a working solution. The model received three inputs through the API: the lesson content, the learner's current code, and structured user context from the primary backend.

It worked beautifully in every demo. Then it shipped, and real users showed up with inputs nobody had tried in a demo. This is what broke, in the order we found it, and what we changed each time.

01

The failure mode nobody demos

The first complaints came through user recordings and support messages. Two failure modes showed up together.

First, SensAI was giving hints that referenced concepts the learner hadn't reached yet, answering around content outside their current progress rather than meeting them where they were.

Second, on simple problems in early lessons, it was handing over the full solution. Not a nudge. The working answer.

The system prompt said "don't give the full answer" but that instruction wasn't specific enough to hold. The fix had three parts: we constrained it to one hint at a time, we anchored hints explicitly to concepts the learner had already progressed through, and we added concrete examples in the prompt showing what an acceptable hint looked like versus what it didn't. Negative examples, showing the model the bad output rather than just describing it, were what actually made the constraint stick.

"Don't do X" in a system prompt is a wish. "Here is what X looks like, and here is what not-X looks like" is a constraint.
02

The hallucination that looked plausible

The subtler failure was the hint that looked plausible but was wrong for the context. The clearest example: SensAI occasionally gave Python-style hints for JavaScript problems. Syntactically confident, pedagogically useless. A learner trying to debug a JavaScript loop would get a hint written in Python idioms, which looked like valid code to someone who didn't know the difference.

The model was inferring the language from context and sometimes getting it wrong. The fix was explicit: we added hard language constraints to the system prompt so the model couldn't drift into the wrong syntax regardless of what it inferred from the learner's code.

Models are confident about things they're wrong about. "Answer in the relevant language" is not a constraint. "This is a JavaScript problem, respond only with JavaScript" is.
03

The latency problem

The pressure we actually felt wasn't cost. It was latency. GPT-4o takes time, and learners who are already frustrated and stuck don't wait gracefully.

We didn't change the model or the prompt to fix this. The fix was entirely on the frontend. While the model was generating, we showed a skeleton state so the interface didn't look frozen. Once the response arrived, we rendered it with a typewriter effect, text appearing character by character rather than all at once. The hint felt faster than it was because the learner was watching something happen from the moment they clicked.

Perceived latency and actual latency are different problems. Sometimes the right fix isn't in the pipeline. It's in what the user sees while they wait.
04

The retry logic we built and threw away

We tried building a fallback store, cached successful hint responses that could be served if a model call failed or timed out, matching on similar cases. The idea was sound. In practice, a hint that was right for one learner's code state was rarely right for another's, even on the same challenge. Context matters too much for caching to work cleanly here.

What we kept was simpler: a hard timeout, and a clean "try again later" message on failure. No retry spiral, no confusing fallback hint. Just an honest acknowledgment that the feature wasn't available right now.

A graceful failure is better than a wrong answer delivered confidently. We ditched the clever solution for the honest one.
05

What the monitoring actually looked like

We built a feedback loop into the UI: upvote, downvote, and a message field. Learners could tell us when a hint was wrong or unhelpful, and they did.

The downvote messages turned out to be the most useful debugging tool we had. When hints started drifting, wrong language, out-of-scope concepts, too much of the solution, the messages caught it before it became a systemic problem. I'd read through the flagged cases, trace what input had produced the bad output, and find the weak spot in the prompt.

By the time I left, the monitoring setup was simple: a monthly check on the downvote messages. Not a dashboard, not automated alerts. A human looking at whether complaints were coming in and what they said. If the downvote rate was low and the messages weren't flagging a new failure pattern, the feature was healthy.

It's not sophisticated. But it caught the real problems. Every prompt fix I shipped came from reading those messages, not from an automated eval.

Your users will find your failure modes before your tests do. Build the feedback channel before you need it.

None of this is exotic. It's the unglamorous half of shipping an AI feature, the half that doesn't show up in a demo and is exactly the half that determines whether the feature is still trusted six months after launch.

The work is: trace the failure modes, read the feedback, fix the prompt, repeat. That's it.
